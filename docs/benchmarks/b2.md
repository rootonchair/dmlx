# B2: Lowest-memory mode (Oct 2026)

Same machine as [B1](b1.md): Apple **M5, 24 GB**, macOS 26.5, under everyday load (other apps
open, 11–16 GB already in swap). FLUX.2 Klein 4B q4 unless noted; 1024×1024, 4 steps.

Three changes, measured together:

1. **Streamed strategy.** The image model (25 blocks) and text encoder (36 layers) keep only their
   non-block weights resident. Each block's weights are read from the safetensors shards on a
   background thread while the previous block runs, then dropped after use. FLUX.2 only reads
   text-encoder layers 9, 18 and 27, so layers 27–35 are never loaded.
2. **Banded decode** for the FLUX.2 VAE. GroupNorm statistics are taken over the whole image, and
   every 3×3 convolution runs in horizontal bands of rows with one row of overlap. The mid-block
   attention is computed a chunk of queries at a time.
3. **Edit precision fix.** mflux's tiled VAE encode returned float32 latents, which pushed the
   whole image model into float32 on every edit below 32 GB. They are now cast to bfloat16.

Before these changes, the cheapest FLUX.2 Klein plan for a new 1024² image needed 4.8 GB, and an
edit took 50–55 s (float32). Edits with one reference now plan with a factor of 1 + 0.75 per
reference instead of 1 + 1.5 (measured 1.45× a plain generation in bfloat16).

## Decoder memory, 1024² (above weights)

| Decode | Peak | Quality vs one-piece decode |
|---|---|---|
| One piece (stock) | ~8.6 GB | reference |
| Tiled, 512 px (previous default below 32 GB) | ~2.2 GB | per-tile GroupNorm statistics: slight colour shift |
| Tiled, 256 px | ~0.6 GB | tile-shaped brightness patches up to ±17 levels: rejected |
| **Banded** | **1.11 GB** (0.37 GB at 512², 2.37 GB at 1536²) | rounding only: mean < 1 level, no 64 px block off by more than 0.2 levels |

Banded decode is not bit-identical to the one-piece decode because MLX picks its convolution
kernel by input shape, so bands accumulate in a different order. A one-band run with stock
GroupNorm math is bit-identical, which confirms the rest of the implementation.

## Exactness

- Streamed and sequential give **identical pixels** when both run uncompiled
  (`test_streamed_matches_sequential_when_uncompiled`). In normal use the other modes run
  mflux's compiled forward pass, so a streamed image can differ very slightly from the same seed
  in another mode (measured: mean 0.96/255). For a fixed seed and mode, results stay identical.
- The streamed text encoder produces bit-identical prompt embeddings.

## Responsiveness (bench probe, no-hang gate: GPU p99 ≤ 250 ms, timer p99 ≤ 50 ms)

| Run | GPU p99 | Timer p99 | Swap-in |
|---|---|---|---|
| Streamed t2i under 2.8 GB ballast (1.2 GB usable) | 1.5–1.6 ms | 10 ms | ≤ 6.4 MB/s |
| Streamed t2i, final build | 1.6 ms | 5 ms | ≤ 19 MB/s |
| Streamed edit, memory-mapped reads (first version) | 86–101 ms | 44–58 ms ❌ | ≤ 11 MB/s |
| Streamed edit, plain reads, no read-ahead | 29–92 ms | 5–47 ms | — |
| Streamed edit, weights kept in RAM (control) | 2.7–3.0 ms | 5–10 ms | — |
| **Streamed edit, final (plain reads + read-ahead)** | **14–25 ms** | **5 ms** | — |

Memory-mapped reads fault in thousands of pages per block and made other processes' timers late.
Without read-ahead the GPU idles during each read, and the next block's long attention kernels
then hold up other apps' GPU work. Reading the next block on a worker thread removes both effects.

## Current-code revalidation (Oct 24, 2026)

The Qwen Image 2.1 lifecycle changes were followed by a fresh 1024² cold/warm matrix on the
same M5 24 GB machine. Every final run used tiled or banded low-memory decode, stayed at normal
memory pressure, and passed the swap-in, GPU-latency, and timer-latency gates.

| Model / task | Strategy | Peak MLX | Wall time | Max swap-in | GPU p99 | Result |
|---|---|---:|---:|---:|---:|---|
| Klein t2i, runs 1–2 | streamed | 1.31 GB | 20.5–21.8 s | 3.3 MB/s | 1.7 ms | pass |
| Klein t2i, runs 1–2 | sequential | 3.39 GB | 18.1–18.4 s | 6.4 MB/s | 1.9 ms | pass |
| Klein edit, 1 ref, runs 1–2 | streamed | 2.02 GB | 42.6–43.2 s | 5.1 MB/s | 24.9 ms | pass |
| Klein edit, 1 ref, runs 1–2 | sequential | 4.09 GB | 37.0–37.2 s | 0.4 MB/s | 3.3 ms | pass |
| Z-Image t2i, runs 1–2 | streamed | 2.14 GB | 55.8–58.8 s | 1.3 MB/s | 1.7 ms | pass |
| Z-Image t2i, runs 1–2 | sequential | 4.05 GB | 53.1–57.3 s | 1.0 MB/s | 1.7 ms | pass |

The matrix found and fixed two cross-model transition issues:

1. A cached prompt could skip the encode callbacks when switching from an eager job to a
   sequential/streamed job. Stale encoder or transformer weights could then overlap reference
   preprocessing. Low-memory jobs now establish their one-large-component invariant at the job
   boundary. The affected Klein sequential edit peak fell from 6.27 GB to 4.09 GB.
2. The rolling swap-in history was not cleared between jobs. A short spike at the end of one job
   could falsely abort the next before it did any work. Each job now starts a fresh pressure
   window; sustained swap-in during that job is still guarded at 64 MB/s.

The current result supports keeping block streaming enabled for Klein and Z-Image. Unlike Qwen
Image 2.1, neither model showed accumulating allocations from streamed transformer blocks.
